Chats and bots

A chat is a long conversation with an agent. A bot is a working directory, a default agent, skills, a speaker and an access profile; a chat on a bot uses them, and a chat on a repository does the repository's work. Both are objects from plugins: chat owns every chat, dev opens one on a repository, and bot opens one on a bot.

Why it exists#

Working with an agent is usually a long exchange, not one command. A chat keeps that exchange in operad: you send messages from the command line, the terminal UI, iOS or Telegram (see Telegram), and every one lands in the same transcript. operad keeps its own record of the messages, so the history of a chat does not depend on the agent's session files; a cleaned or compacted session does not erase it.

A bot exists for chats that are not about a repository. It fixes, in one place, the working directory, default agent, skills, speaker and access profile that such a chat uses, so you can keep several bots with different permissions, for example a read-only one. Because a chat reads its bot at every reply, tightening a bot or adding a skill does not need a new chat.

A bot's directory is $OPERAD_HOME/bot/<name>; the default bot is $OPERAD_HOME/bot/default, beside the other bots rather than above them. Its memory/ directory is made when missing; the memory plugin gives it a git history and mounts the memory skill for every bot, and the shared wiki is outside a bot's directory so all bots use one. See Memory and the wiki. A bot may read and write its own directory and its memory, and every other bot's directory is refused for reading and writing. The default bot's old home at $OPERAD_HOME/bot is not emptied: only the skills/ and memory/ directories operad made there move into $OPERAD_HOME/bot/default. Every other file and directory a person or the bot put in the old home stays where it is, and the default bot may still read, write and run there; only another bot's directory is refused. Grants in access-user.json whose working directory is exactly the old home are rewritten once to $OPERAD_HOME/bot/default; grants for other directories are unchanged. A bot with a written cwd keeps it.

The plugins are deliberately cautious. A chat on a repository is read-only until you agree to open a worktree (unless the repository sets workIn to branch: then the chat works in the main clone at its access level; the same in a folder without git, where there is no worktree to open and the chat may change the folder's files at its access level). A bot cannot change its own skills, settings or MCP servers; it can only propose a change, and nothing on disk changes until a person approves.

How it works#

  1. A chat is opened by a plugin: dev:chat on a repository, bot:chat on a bot. The agent is chosen then and does not change; the model, effort and access level can be changed later with chat:model, chat:effort and chat:access.
  2. chat:send records a message. A message is an event whose source is ios, telegram, cli, tui or other, and the chat plugin's own rule starts chat:reply for it (see Chats).
  3. chat:reply takes the messages that no reply answers yet from the chat's own record, continues the agent's session, and records the reply. A message sent while the reply is being written is given to the agent in that same reply when its agent takes messages mid-run (claude, pi, codex); otherwise, or when it has an attachment, it waits for the next round as a queued message. If messages are still waiting it goes round again, at most 20 rounds. Without operad serve the message is only recorded and is answered when serve runs. A reply being written can be stopped; its half-written text stays in the transcript, and /retry answers the last message again after a failed or stopped reply. A pi chat retries a failed model request by itself with pi's bounded backoff; the live transcript shows the attempt, the time of the next try and why, and a successful retry leaves no line behind.
  4. While the agent works, the transcript section shows the messages, tool calls and the unfinished text of the current reply.
  5. Each tool call is checked against the chat's access profile with the chat's access level composed into it (see Access and Access level). For a bot chat the profile is the default profile plus the bot's own access settings; the bot's settings are read again at every reply (see Bots).
  6. A chat on a repository starts in the main clone as read-only. A write, or a command that is not known to only read, becomes the worktree question, which offers Allow once, Always allow, Deny and opening a worktree; the worktree offer has dev open work/chat-<id>, ends the asking reply and answers the same message again there, so the agent continues with write access.
  7. When a bot proposes a skill, a settings change, an MCP server or a routine (operad bot skill, bot setting, bot mcp, bot schedule), a bot-proposal object waits in Pending. bot:approve applies it and bot:reject drops it (see Bot objects and proposals).
  8. chat:close records chat.closed; the transcript stays readable and chat:send is refused.

Chats#

A chat belongs to the plugin that opened it. dev opens one on a repository:

operad dev:chat --repo operad --title "The build" [--agent pi]
operad chat:send C-0001 --note "why does the gate fail on main?"
operad show C-0001 --section transcript

dev:chat offers claude and pi as agents (the first one loaded when --agent is left out): they can stop a tool call before it starts, which a read-only chat needs. radian is refused there as an agent and stays for bot chats. A repository chat starts at plan; a bot chat starts at the bot's bot.bots.<name>.accessLevel (ask unless set), except a run of a routine, which starts at full. The access level is changed in the chat with /access <level> (see Access level). bot:chat offers every loaded agent; its default is the bot's harness, or the first loaded.

A message is queued from when it is sent until a run takes it: the messages of a run's first prompt are taken when it starts, and a message handed to an agent mid-run is taken then. A chat's row and its transcript section carry the queued messages in data.queued, in sending order, with data.queuedCount; the row and the section have neither field when nothing is queued. A client shows "N queued" above the composer and offers chat:withdraw and chat:edit on each of them. A message a run has taken never changes, and both actions refuse it with a line naming the message.

A line that starts with / and names one of the chat's actions runs that action instead of going to the agent: /model sonnet, /effort high, /access edits, /stop, /new, /new <what comes next> (the new session starts with a short brief of the old one for that goal), /private (a bot chat only; see below), /retry, /status, /close, /help. chat:withdraw and chat:edit are actions of the queued message, not chat commands. The rest of the line is the action's arguments, in the order its fields are declared; one field takes the whole rest, and with more than one the last field takes what is left. A /xxx that names no action, or a slash later in the line, is an ordinary message. /close asks for the action's confirmation: /close alone does nothing and says to send /close yes. /help lists the actions this chat accepts, each with its one-line description, then the skills it can type by name. Every attempt leaves one entry in the transcript, naming who typed it, the line and what happened or why it was refused; that entry is not a message, so the agent never sees it. A command runs at once while a reply is being written and does not start a reply of its own. A command works from every client because chat:send handles it.

A chat's skills are typed as /name rest too. A bot chat can type its bot's skills; a repository chat can type the skills its dev.json gives it. When the name is not one of operad's commands, the line is an ordinary message to the agent: an agent that loads skills itself gets /name rest unchanged, and any other agent gets the skill's SKILL.md body in the prompt, after a line naming the skill and before rest. The transcript keeps the line as typed. A skill whose name is an operad command yields to the command. The chat's view carries skills: [{ name, description? }] beside its actions, so a client shows the skills and the commands from one GET /v1/objects/<id> (or MCP show); each description comes from SKILL.md.

A message is an event: source ios, telegram, cli, tui or other, key is the message id, object is the chat. A routine's first message has the source bot, and the bot plugin's own rule starts chat:reply for it. The chat plugin's own rule starts chat:reply for the client sources automatically; a rule of yours in triggers.json with the same source and type replaces it. The reply reads the messages no reply answers yet from the chat's own record, continues the agent session, records the reply, and goes round again while new messages still wait (at most 20 rounds). An ordinary message sent during the reply is given to an agent that takes messages mid-run in the same reply; a command still runs at once and never reaches the agent. After a restart a reply that was already recorded is not given twice.

The transcript section is live: it shows user messages, the agent's intermediate text, Thinking, tool calls with their result, duration and a short output, and the final reply. It shows a reply's lines and any message the reply takes during it in the order they happened: what the agent did before the message stays above it and what it did after stays below it, and the message that started the reply stays above all of them. A message the reply does not take waits for the next round and shows below the finished reply. An older chat whose lines were recorded without a time keeps the order it was recorded in. It also carries how full the agent's context is (used, the model's window when known, and the model) from the last finished reply; the chat's object view carries the same context. A new session leaves it out until the next reply. The clients label it with the approved words Context used and 上下文用量. A reply that fails leaves one line saying it failed and why, so a failure is not mistaken for a slow reply. Tool output is cut in the transcript; the full output is in a file in the chat's directory. A reply that is still being written shows its unfinished text and thinking as a tail; mark and after let a client append only the finished part (see Reading a section). While a pi chat waits to try a failed model request again, the live section also carries retry: the attempt, how many there are, when the next one starts and the provider's reason, so a client can count down. The records do not depend on the agent's own session files, so a cleaned or compacted session does not erase the chat's history; the agent's context still belongs to the agent, which continues its own session.

A pi chat compacts its context after a reply when it reaches three quarters of the model's window. If the compacted context still fills that much, the chat does not compact again and again: your next message fails with a line saying the chat is too full to continue. Send /new to start a fresh one.

A stretch that is not remembered#

In a chat of a bot, /private starts a stretch the bot does not remember, and /private again ends it. While it is on the chat shows "Not remembered / 不记入记忆". The messages stay in the chat and you still see them; this is not deletion and not a separate chat. They do not enter the bot's memory: the bot cannot write a note during the stretch (it can still read its notes), the memory flush before a compaction is skipped, Dreaming leaves the messages out, and they are not in the search index, so the bot cannot find them again. The chat answers /private with one of two lines, and Telegram shows the same line when the stretch starts and when it ends:

  • On: Not remembered / 不记入记忆: on. Messages from here stay in this chat but are not saved to memory or search. Send /private again to end it.
  • Off: Not remembered / 不记入记忆: off. What you sent meanwhile was not saved, but this chat may still recall it. Send /new to start clean.

The command is refused while a reply is being written.

The stretch is still in the agent's own session. A compaction could carry it into later context, so when you end the stretch the chat suggests /new; until then the memory flush is skipped for that session.

A chat's filters are open (the default) and closed; the kernel adds all, so operad list chat --filter all still shows closed chats. A chat on a repository whose workIn is worktree works in the main clone, read-only (with workIn branch it works there at its access level, below): a shell command runs there only when it is on a short list of commands that only read (git status, ls, cat, grep, sed -n, bun test, ...); every other command, and every write or edit, becomes the worktree question, which names the command or the path. The question offers Allow once (this call only), Always allow (the exact call and working directory go into access-user.json, so it is not asked again in any chat), Deny, and opening a worktree. Deny tells the agent the call was refused because the chat is read-only, and that it should answer in the chat or use read-only commands. The worktree offer has dev open work/chat-<id>, and the chat works there from then on, once; the main clone otherwise stays read-only. The reply that asked ends, and the same message is answered again in the worktree, so the agent continues there with write access: a chat at plan moves to edits with it. A yes that comes after the reply has ended opens the worktree but starts no second reply. The transcript says This chat now works in a worktree. once. The worktree's changes reach main only through a task that points at it, through the normal gate and integrate.

Attachments are files a client uploaded (POST /v1/uploads), stored under the chat's attachment directory in the operad home. A message may be only files. The transcript shows each as a line with its name (an image as an image, another file as an Attachment: link). The reply gives an image to claude and pi as image input (up to 5 MB each) and every file to the agent as a path in the prompt; the chat's access profile gains read access to that chat's attachment directory and nothing else. The MCP tools cannot pass a file; a client uploads it.

The agent reaches operad through its tools (list, show, section, pending, answer, running, history, command, act, under the same allow lists as operad mcp), never by running operad in a shell.

Access level#

Every chat has an access level: plan, ask, edits or full. /access <level> changes it, or operad chat:access <chat> --level <level>; the level is recorded on the chat and every tool call from then on uses it, including a reply already being written, across restarts and clients. A question open when the level changes is checked again under the new level. A repository chat starts at plan (read-only) and a bot chat at the bot's accessLevel setting (ask unless set; one of plan, ask, edits, full), except a run of a routine, which starts at full. A chat nobody ran /access on follows the setting at its next reply, so changing the setting moves it; a level a person chose stays. The row shows the level when it is not the chat's starting level. In a repository whose workIn is branch ("A branch in this folder") a repository chat works in the main clone, on the branch that is checked out, at its level: edits and full write there, no worktree is offered and no work/chat-<id> branch is made, and plan stays read-only. While a task holds the folder (running, waiting for you, ready to merge or paused), a reply is read-only and the chat says a task holds the folder. With worktree ("A separate worktree", the default) the rest of this paragraph applies. A repository chat that still works in the main clone and is raised to edits or full first opens work/chat-<id> and moves there; if the worktree cannot be opened the level stays as it was and the command says why. A chat already in its worktree applies the level there. plan and ask never open a worktree, and ask in the main clone keeps the worktree question for a write. A bot chat at any level works in the bot's own directory, with no worktree.

LevelWhat runs without asking
planReading, and commands known to only read; a write asks.
askReading; every write and every command not known to only read asks.
editsReading and writing files in the working directory; a command not known to only read asks.
fullEverything except a call a deny refuses, a write or command a read-only working directory asks about, and a write under readPaths; the level adds no question, and ask commands, ask paths, unlisted MCP tools and outward-write questions do not ask. A command the matcher cannot follow (inline code, a shell expansion, a path after a directory change it cannot follow) runs too, unless a deny plainly matches.

The profile's deny lists still hold at every level, and readOnly and a write under readPaths still ask. Below full, its own askCommands and askPaths rules still ask. At full they do not, and a background run does not ask before an outward write: only a deny, readOnly or a write under readPaths can stop a call. The approved words in the interface are Access for the menu, and Plan only, Ask each time, Accept edits and Full access for the levels. claude and pi carry every level; a chat whose agent cannot carry a level refuses the reply with a message naming the level instead of ignoring it. See Access for the profile itself.

Bots#

The bot plugin has no tab. Its objects live under Settings: a bot page is that bot's settings page, and the bots are listed in a section named Bots. A bot is written in config.json under plugins.bot.settings; the default bot exists even when it is not written. The section is read at every use, so an edit applies to the next reply without a restart.

A bot is created by the bot:create action on an existing bot. It takes the new bot's name and agent, optionally its model, effort and speaker, and the skills and MCP servers to give it. The skills offered are the ones another bot already mounts and the skills in ~/.agents/skills when it exists; a path may be given instead. The MCP servers offered are the ones a person already approved on another bot: each is copied with its pin, tools, digest and secret names, and is not asked about again. The new bot has exactly what was chosen; nothing is inherited from default, and one that chooses none has no skills and no servers. A name is checked like any bot name, and an existing one is refused. The result opens the new bot, and names the secrets a copied server needs before it starts. The page of the new bot shows its skills by name and its MCP servers.

Using your own agent settings#

A bot has useOwnSettings, titled Use my own agent settings, off by default. When it is on, the bot's agent reads your own configuration of that agent. The switch is read at every reply, including for messages that arrive from a channel such as Telegram; with it off nothing changes for claude or pi.

claude. The settings from ~/.claude/settings.json, project and local Claude settings, CLAUDE.md instruction files, auto memory, allow and deny rules, hooks, skills, commands, subagents, plugins and MCP servers. Telemetry, error reporting and background tasks stay off, and a reply is still one foreground turn. Before any allow rule in your settings can approve a tool call, the call is judged in the PreToolUse hook the claude harness already runs: a path, command or read-only refusal of the profile denies it. A call the profile allows and your settings allow runs without a question; a call the profile says to ask is asked through operad as before. operad's own tools, the skills the bot lists, the MCP servers the bot lists and its log hooks stay; when both sides define a skill or an MCP server, operad's is the one used. The MCP servers in your own Claude configuration are available to the bot without the bot's MCP approval. Hooks from your settings run on the bot's tool calls after it is on, and the bot's access profile is judged first.

pi. Your pi settings and resources from your pi directory (~/.pi/agent, or what pi's PI_CODING_AGENT_DIR names): settings, context files (the global AGENTS.md of pi and those pi finds from the working directory), skills, prompt templates and extensions. Nothing is copied into operad's directory. The session stays operad's, under the operad home, so a chat still finds it; the model and login are yours as before. operad's inline extension and tools stay, and a skill the bot lists wins a skill of the same name in your pi. Every tool call, including one from a tool your extension added, is judged by the access profile in the tool_call hook before it runs; a tool the profile cannot check is refused while the profile has rules. An extension also runs its own code in the worker process: code it runs at load, its own child processes and its own network calls are not tool calls and cannot be stopped by the profile. Your pi's compaction settings stay off. A chat reply turns pi's automatic retry on, using your attempt count and delays when your pi settings name them and pi's defaults otherwise; a task keeps it off.

codex. Codex reads your own Codex configuration whether the switch is on or off, because a bot starts your own codex app-server: ~/.codex/config.toml with its model defaults, hooks, rules and MCP servers, the AGENTS.md instruction files Codex reads, and the project settings it applies there. operad adds its thread sandbox, approval policy and MCP servers. The switch changes nothing here. The access profile answers the approvals Codex asks operad about; a command that stays inside Codex's own sandbox is bounded by that sandbox, not by the profile.

radian. Radian reads your own radian configuration whether the switch is on or off, because a bot runs your radian exec: RADIAN_CONFIG or ~/.radian/config/config.toml with its model, permissions, skills, hooks and MCP servers, the global and project context files it discovers (AGENTS.md and the other names it reads), and trusted project resources. operad gives it a copy of that config with its PreToolUse hook and its own MCP config. The switch changes nothing here.

Bot objects and proposals#

A bot page has the bot section. A bot that cannot be used stores its problem and its row says so; bot:chat then refuses with that problem. A bot taken out of the settings is marked removed; a new one appears at the next use.

A change a bot proposes to itself is a bot-proposal object. It is pending until a person approves or rejects it; nothing on disk changes before that. A proposal is one of:

  • a skill (bot skill): the files before and after, applied to the skill directory and added to the bot's skills;
  • a settings change (bot setting): the bot's settings before and after;
  • an MCP server (bot mcp): a new server, an upgrade, or a server whose tools changed;
  • a routine (bot schedule): adding, changing or removing one routine, shown with its name, schedule in words and as cron, prompt, model and effort.
  • Set up git here (bot setup-git, for the bot's agent): see Set up git here.

Set up git here#

A folder without git, or a computer without the git program, can be added and chatted with, and the chat may change its files. Git is needed only to create a task, and the bot asks nothing about git before that. When you ask for a task in such a folder, operad says what is missing and the bot offers Set up git here (在这里设置 git):

  • If git is not installed, the bot gives the command for your system (xcode-select --install on a Mac, winget install Git.Git on Windows, the package manager on Linux). Each command is a pending item you approve; operad does not bundle git.
  • It then proposes the first commit as one pending item. Its review shows the .gitignore (your own is kept, with lines added), the list of files the commit would hold, any folders that are repositories of their own (not committed), and the name and email the commit is made with, prefilled from the computer account; the bot asks you to confirm them in the chat. When git already has a name and email on the computer they are used and not asked for. A folder of more than 5000 files carries a note to check the .gitignore first. Your home folder and a disk root are refused, and so is a folder inside another git repository (the answer names that repository's folder).
  • Approve starts git in the folder when needed, makes the first commit of exactly the files listed (a file a chat wrote after the review is not in it) and stores the name and email in the folder's own git settings. The folder then works in a branch with no remote; nothing is pushed. Reject changes nothing.

bot:approve applies a pending proposal and bot:reject rejects it. A proposal that is not pending still shows its state. The bot-proposal filters are pending (the default), applied and rejected; each pending proposal is also a pending item of its bot, so it appears in Pending and in the app.

Bot commands#

operad bot skill <bot> <name> [--from <dir>] proposes a new or changed skill. Without --from, stdin is a JSON object with skill_md and files; with it, the directory's files are read. The skill needs a SKILL.md. It prints proposed skill "<name>" for bot <bot>; review it in pending.

operad bot mcp <bot> <name> <command> [args…] starts a local MCP server once, reads its tool list and proposes registering it. With no command, stdin is a pasted mcpServers entry. Only a local server (a command with arguments) can be registered; an address (url, type: "http", type: "sse", headers) is refused. A package command must name an exact version: npx -y pkg@1.2.3 is accepted; pkg@latest or a range is refused with the version it needs. The server is started in the bot's working directory with the bot's access profile and its secrets. It prints proposed MCP server "<name>" for bot <bot> (<n> tools); review it in pending.

operad bot setting <bot> reads a JSON object from stdin and proposes the change. It cannot add or change mcpServers; that is what bot mcp is for. It prints proposed settings for bot <bot>; review it in pending.

operad bot schedule <bot> add|edit|remove <name> proposes a change to the bot's routines. add needs --schedule <cron>, --words <schedule in words> and --prompt <text>; edit needs at least one of --schedule, --prompt, --model and --effort, with --words; remove takes the name and --words. Optional --model and --effort set or clear those fields. It prints proposed routine "<name>" for bot <bot>; review it in pending. A chat's agent calls this command through operad's command tool; a schedule it writes is a proposal, never an immediate routine.

Routines#

A bot can hold routines. The user word is Routine (Chinese 定时任务). A routine has a name, a five-field cron schedule in the machine's local time zone, the prompt, an optional model and effort, and whether it is paused. Routines are their own list, Routines: each row shows the routine's name, its bot's name, the next run and the last result (done, nothing to report or failed). A routine's page shows the prompt, the schedule and its runs as history; each run is a section with its process and result. The bot page lists its routines too.

Each bot also has Dreaming (Chinese 梦境整理), a built-in routine for its nightly memory tidy (see Memory). It is in the list with its next night, last result and runs, and it is not edited, paused or removed there: its time is the bot's tidyTime, and the setting runWithoutAsking chooses whether it first shows a pending card and waits for Run or Skip.

To schedule something from a chat, say it in words ("every morning at 8, collect the day's news"). The bot writes a proposal with the name, the schedule in words and as a five-field cron expression, the prompt, and the model and effort. It waits in Pending: bot:approve adds it, bot:reject drops it, and until then no routine exists. Editing or removing an existing routine from a chat is a proposal too; a change made through the actions below is your own edit and applies at once.

On a routine's own page the actions are bot:edit (optional schedule, prompt, model, effort), bot:pause, bot:resume, bot:run-now and bot:remove; they take no name. Add is on the bot. The command line, HTTP and MCP also keep the older bot actions, which take the routine's name and mean the same:

operad bot:schedule-add default --name Morning --schedule "0 8 * * *" --prompt "Collect the day's news."
operad bot:schedule-edit default --name Morning --schedule "0 9 * * *"
operad bot:schedule-pause default --name Morning
operad bot:schedule-resume default --name Morning
operad bot:schedule-run-now default --name Morning
operad bot:schedule-remove default --name Morning
Action on the botArgumentsWhat it does
bot:schedule-addname, schedule, prompt, optional model, effort, pausedAdds a routine. The name is unique on that bot; the schedule is a five-field cron expression in local time.
bot:schedule-editname, optional schedule, prompt, model, effortChanges a routine. A changed schedule starts fresh, so no time missed under the old schedule is caught up.
bot:schedule-pausenameStops it running; a paused routine collects no missed times.
bot:schedule-resumenameLets it run again at its next planned time.
bot:schedule-run-nownameRuns it once now, as a timed run would (clients label it "Run now", 立即运行): the prompt with the recent results and the quiet-ending line, a notification unless it ends quietly. The next timed run is unchanged. An unknown name is refused, and so is a routine whose previous run is still replying.
bot:schedule-removenameRemoves it.

When a routine runs, the bot starts a run under itself and sends the prompt as its first message. A run is not a chat: it has no chat id, is not in the chat list and cannot be continued; it is a section of the routine's history, with its process and result. It runs as the bot, with its skills, MCP servers and access profile, and starts at full: only the profile's deny rules, readOnly and a write under readPaths can stop a call; an ask rule and an outward write do not ask. Its first message has no person's source, so that reply is a background run: at a level below full an outward write in it asks. A routine keeps its runs for 30 days.

After serve has been down or the machine has slept, the latest missed run in the last seven days runs once; older ones are skipped. A catch-up run adds one line to the prompt saying when it was planned and how late it runs.

When the reply ends, the routine's last result is a short summary of it, and the notify command runs with that summary as OPERAD_REASON (see Notifications). A failed reply records and notifies its failure line instead.

Every routine ends its prompt with a line telling the agent how to end quietly: a reply that is exactly NOTHING_TO_REPORT (surrounding blank space ignored) means there is nothing new. The notify command is not run for that run; the routine's last result reads "Nothing to report.". Any other reply, and every failure, notifies as above.

The prompt of each run also carries the last three results of the same routine (each cut to 120 characters, quiet ones included) and asks the agent not to repeat what the person has already seen.

Routines from before this change are moved to routine objects the first time the server starts, and the chats those scheduled prompts and the memory tidy had opened are closed once.

Follow-ups#

A Follow-up (Chinese 跟进) is a one-time deadline an agent sets for itself in a chat: "look at this again in two hours". It has a due time, one sentence of what to do, and the chat it was set in. A routine is yours and recurs; a follow-up is the agent's own and happens once.

The agent sets one with the bot follow-up command (operad bot follow-up <chat> --at <time> --do <sentence>), which the chat's first-session line tells it about. The time is absolute (2026-12-01 09:00, local time, or an ISO time) or relative (+30m, +2h, +3d). It takes effect at once and does not ask you first. Limits: at most 5 follow-ups not yet due in one chat, and a due time at most 30 days ahead; a refusal names the limit that stopped it.

When it is due, the sentence is sent into the same chat, so the reply continues that chat's session. The message does not come from a person, so the reply is a background run: below full access, an outward write still asks (see Access). If serve was down at the due time, the follow-up is sent once after it starts, with a line saying when it was set for and how late it is. A follow-up whose chat was closed is dropped.

The bot's page lists the follow-ups not yet due, and the bot's row carries them in data.followUps (see HTTP). bot:follow-up-cancel <bot> --id <id> cancels one; the agent lists and cancels its own chat's with operad bot follow-ups <chat> [--cancel <id>]. A cancel is not a proposal.
