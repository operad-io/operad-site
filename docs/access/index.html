Access

An agent asks before it runs a command or touches a path its access profile does not allow. A person answers the question with an action; allow_always records the call so the question does not come again. The profile is a guard rail, not a boundary: it matches the text of a call, and a program that builds a path or command another way is outside what it can see.

Why it exists#

An agent can run shell commands and edit files, and you will not read every call before it runs. An access profile lets you write down in advance which paths and commands are refused, which ask a person first, and which run freely. The default profile covers the common cases: credentials, the operad home, destructive commands, and a few commands that change the machine.

The profile is a guard rail, not a boundary. It matches the text of a call and cannot see what a program does once it runs, so it makes no claim to stop everything. For commands that hide what they run, such as bash -c, it asks or refuses instead of guessing.

How it works#

  1. Before an agent runs a tool, the harness gives the call to the matcher in packages/access-match together with the profile. A call is a tool name, its input and the working directory.
  2. The matcher applies the order deny, then ask, then allow. A match in denyPaths or denyCommands refuses the call. A match in askPaths or askCommands, or a write in a readOnly working directory, asks a person. Anything else runs. See The profile.
  3. A path is normalised first: ~ is the user's home and a relative path is joined to the call's working directory. A command is split into its pipeline parts and each part is matched. Inline code is refused or asked about, because its content cannot be seen.
  4. For an MCP call the matcher looks at allowMcp when the field is present: a listed tool runs, an unlisted one counts as a write and asks (see MCP tool entries).
  5. A question goes to a person, who answers allow_once, allow_always or reject_once. allow_always appends the exact command or path and the working directory to access-user.json, and the next identical call in that directory is allowed without a question (see allow_always). It never lifts a deny.
  6. In a background run, no person started the run, so alwaysAllow entries are ignored and every question is asked again.

The profile#

A profile is a JSON object. A bot's profile is its bot settings merged with the default below; a flow's profile is given to the steps that declare they enforce its fields. The matcher applies this order: deny wins over ask, and ask wins over allow. A call that matches a deny is refused whatever an ask rule says; a call that only matches an ask rule asks a person; every other call is allowed.

The fields cwd, outside and network are not read by the matcher. The MCP entries say what a local or remote MCP tool may do; see MCP tool entries.

denyPaths and askPaths are matched against the path as the call wrote it, normalised with ~ as the user's home and relative paths joined to the call's working directory. A path under a denyPaths entry is refused. A write or edit under an askPaths entry asks; a bash redirect to one asks with the whole command.

readOnly makes the call's working directory read-only: a write or edit there asks, and a bash command asks unless it is on the short list of commands that only read. A deny still wins.

readPaths lets a read reach a directory under an ancestor in denyPaths. It does not allow a write: a write there asks.

The default profile#

The default profile is what a bot starts from. Its lists are added to the lists a bot writes; a bot can tighten them, never loosen them.

ListEntries
denyPaths~/.ssh, ~/.gnupg, ~/.aws, ~/.config/gh, ~/.radian, ~/Library/Keychains, ~/Library/Application Support/Google/Chrome, ~/Library/Application Support/Firefox, ~/Library/Safari, .git/config, .git/hooks, and every entry of the operad home except the bot's own directory (the names there now, and store, secrets, config.json and the MCP report directory)
denyCommandsoperad, sudo, su, rm -rf /, rm -rf ~, mkfs, dd, diskutil, shutdown, reboot, launchctl, crontab -r, git push --force*, git push --delete, curl … | sh, wget … | sh, pkill, killall

readPaths, readOnly, allowMcpabsent

The home entries are absolute, so a home other than ~/.operad is covered too. The bot's own working directory under ~/.operad/bot is the one part of the home the agent may use. The path of a repository dev knows, and the path of a bot's skill directories, are added to denyPaths: the agent reaches a repository through dev's actions, not by touching its files. A bot's own access lists are appended to these, and its access.readOnly can turn the working directory read-only.

A rule is a pattern of words; * matches any characters in a word. -rf matches the same single-dash letters in any order, and … adds no condition. git push --force* therefore matches git -C x push --force. An inline command (such as bash -c, python -c, bun -e, osascript -e, find -exec, xargs, eval, a backtick or $()) is refused while denyCommands is set, and asks while only askCommands is set, because the matcher cannot see what it runs. The full rule tables are in packages/access-match/REFERENCE.md.

access-user.json#

$OPERAD_HOME/access-user.json (see the home) holds the calls a person answered allow_always for. A missing file is an empty list. A file that cannot be read is reported by the step that reads it and treated as empty. A person adds an entry by answering allow_always; removing an entry is deleting its object from the array. The file is written under a lock and replaced whole, so a crash does not leave it half written.

[
  { "kind": "command", "value": "git status --short", "cwd": "/Users/you/Code/example" },
  { "kind": "path", "value": "notes/todo.md", "cwd": "/Users/you/Code/example", "tool": "edit" }
]

An invalid file is treated as an empty list and the step logs the user access file "<path>" ...; it is treated as empty. An allow_always answer writes an entry only when the call was allowed once; a call that holds a secret value is never asked about and never written.

allow_always#

When a call needs to ask, a person sees three choices in a run a person started (allow_once, allow_always, reject_once). allow_always lets this call run and appends its exact value and working directory to access-user.json; later calls with the same text in the same directory then run without asking. It does not lift a denyPaths or denyCommands match, and it does not cover a different command, a different path spelling, or the same command in another directory. A late answer may carry the write too; if the file cannot be written, the step logs that and lets the call run once.

MCP tool entries#

allowMcp in the profile (or mcpAllow in a bot's settings) lists the MCP tools that run without asking, as <server>.<tool> or <server>.*. The field's presence, even as an empty list, puts MCP tools under the profile: a tool that is not listed counts as a write and asks first. A tool that is listed runs without asking; a deny path or command still wins when it covers the call.

An answered MCP question is recorded like any other command: kind is command, value is mcp <server>.<tool> and cwd is the working directory. An entry matches only that server and tool, exactly.

Background runs#

A run is a background run when no person's message started it: a schedule, a webhook, an incoming message from another source, or an event a run emitted. Only a message from one of the chat's own client sources (ios, telegram, cli, tui, other) is a person's message for this rule.

In a background run the existing alwaysAllow entries are not used, and allow_always is not offered: a question asks again every time, with allow_once and reject_once only. This is deliberate: a scheduled or incoming run is held to the profile afresh rather than inheriting a permission a person gave in an earlier conversation.
