MCP server

operad mcp is a Model Context Protocol server on stdio. It gives a lead agent typed access to the same objects, lists, sections, pending items, running items and history that operad and the /v1 interface read. It also runs plugin verbs and the lead actions config.json allows, through the same paths as the CLI. It never starts a step or takes an owner decision; only operad serve runs steps, and the actions left out of mcp.actions stay in the command line or the app.

The server implements the MCP JSON-RPC 2.0 transport, protocol version 2025-06-18. It has no runtime dependency except @operad-io/engine.

Why it exists#

A lead agent such as Claude Code needs to see what operad holds (objects, pending items, running items, history) and sometimes to act on it. Without this server it would have to run operad commands and parse their output, or call the /v1 interface itself. The server gives it typed tools over the same data, and the same lead actions, so what it reads and does matches the command line and the app.

It is deliberately limited. It never starts a step and never takes an owner decision: only operad serve runs steps, and an action runs from here only if you list it in mcp.actions. The optional channel exists so the lead hears when something changes, such as a wait that opens, instead of polling; it is one-way and relays no permission prompts.

How it works#

  1. The client starts operad mcp from an entry in .mcp.json (Setting it up). The server reads the home named by $OPERAD_HOME, or ~/.operad, and speaks JSON-RPC on stdio (Transport).
  2. The client sends initialize, then calls tools. The read tools (types, list, show, section, pending, running, history) return the same data as the matching commands and /v1 calls (Tools).
  3. command runs a plugin verb as operad <plugin> <verb> would, with input standing in for stdin. act runs an action through the same path as POST /v1/act, recorded with the actor { "via": "mcp", "id": "lead" }.
  4. Before act runs anything, the server checks mcp.actions from config.json. An action not listed is refused with a message that says the owner runs it. An action that asks to confirm also needs mcp.confirmActions. show lists the refused actions under ownerActions, so the lead can tell you what to run.
  5. answer replies to a pending item for a run that waits. When every choice is also an action on the object, the answer runs through that action, so the same allow list and confirmation apply.
  6. A malformed request gets a JSON-RPC error; a refusal from the data itself comes back as a normal result with "isError": true (Errors).

With operad mcp --claude-channel the server also sends notifications/claude/channel:

  1. At start it reads the current rows of the object types it covers and sends nothing for them.
  2. It then watches the objects and the flows, because a wait that opens or a step that starts changes no object. A change another process makes is found by polling.
  3. After the client sends notifications/initialized, it sends one line for each wait that opens, each object that reaches a final state, and each object that reaches the same state loopAfter times with no wait or end between. Which of these are sent is set by mcp.channel.notify (Claude Code channel).
  4. The client then reads the details with show, section, pending or history.

Setting it up#

operad mcp runs an MCP server on stdio for a lead agent. It reads the same objects, pending items, running items, sections and history as the commands, and it runs the plugin verbs and lead actions config.json allows. It never starts a step or takes an owner decision; only operad serve runs steps, and the actions left out of mcp.actions stay in the command line or the app. The protocol, tools and error mapping are below; stdout carries only JSON-RPC and logs go to stderr.

Claude Code finds the server in a project .mcp.json:

{
  "mcpServers": {
    "operad": {
      "command": "operad",
      "args": ["mcp"]
    }
  }
}

The server uses $OPERAD_HOME, or ~/.operad when it is unset. Set OPERAD_HOME in the entry's env when the agent should read another home.

Turning the channel on#

operad mcp --claude-channel turns the server into a one-way channel: it declares the experimental claude/channel capability and sends notifications/claude/channel when an object's state, waiting flag or running flag changes. It never declares claude/channel/permission and never relays a permission prompt. Without the flag the server sends no notification and declares no experimental capability.

The server watches both the objects and the flows, so a wait that opens or a step that starts is reported even when no object is written (a change another process makes is found by a poll, 500 ms by default). It sends nothing until the client has sent notifications/initialized, then sends what changed since the start. At start the server reads the current rows and sends nothing for them. Every later notification has a one-line content, <id> <old state> -> <new state> with : <note> when the row has one, and string meta with id, type, state, previous, waiting and running. An object seen for the first time after the starting read has previous set to new. The channel is one-way; use show, section, pending and history for the details.

--types <t,…> limits the channel to some object types, separated by commas. The default is every type with views; a name that is not one is a usage error. For example:

"args": ["mcp", "--claude-channel", "--types", "task"]

Claude Code enables the extension with its development-channel flag, naming the server from .mcp.json:

claude --dangerously-load-development-channels server:operad

Transport#

Messages are one JSON-RPC object per line, incoming on stdin and outgoing on stdout. A message must not contain an embedded newline. stdout carries only JSON-RPC messages; plugin loading, view errors and other logs go to stderr.

The server accepts these methods:

MethodWhat it does
initializeReturns the protocol version, the tools capability, the server name and version, and the instructions.
notifications/initializedAccepted; it has no response.
pingReturns {}.
tools/listReturns the tool table below.
tools/callRuns one tool.

The initialize result carries this fixed instruction:

The operad MCP server reads objects, pending items and history, and writes the commands and lead actions it is allowed to. Owner decisions are not offered here.

tools/call takes { "name": "<tool>", "arguments": { ... } }. The arguments are checked against the tool's input schema before any view is read. A missing required field, an unknown field, or a field of the wrong type is a malformed request.

Claude Code channel#

operad mcp --claude-channel also pushes object changes to a client that understands Claude Code's channel extension. Without the flag the server has the same tools, capabilities and instructions as before, and sends no notification.

With the flag the initialize result carries capabilities.experimental["claude/channel"] = {}. It never declares claude/channel/permission: the server relays no permission prompts. The instructions gain a paragraph saying the channel is one-way and the read tools give the details.

There are two sources. One is the store's object changes. The other is the changes to flows, because an object's waiting and running flags come from its flow: a wait that opens or a step that starts writes no object. Both use a directory watch with a polling fallback, so a change another process makes is seen too (the poll interval is the store's and the flow records' own, 500 ms by default). Each change re-reads that object's row. At start the server reads the current rows of every type that has views and sends nothing for them; if it cannot read a type's rows, the first row it sees for each object of that type is its baseline and also sends nothing. It remembers the last row it saw for each object and sends a block only for one of three things (mcp.channel.notify below):

  • waiting: the waiting flag turns on. The content carries the row's note, which holds the reason when there is one (rework limit, work failed, ready to merge). A wait the object's own plugin answers automatically is not announced: dev does this for a task whose plan is at auto merge and whose review passed, because dev answers "merge" a moment later. The kernel asks the plugin (the object type's answeredAutomatically hook) each time, and the pending item carries auto: true for the channel only. If the answer does not come (dev refuses it, or the plan's auto level changes) the next change finds the wait unmarked and the block is sent then. A wait the plugin does not answer (rework asked, work did nothing, review failed twice) is sent as before.
  • ended: the object reaches a final state. The plugin declares which states are final by setting final: true on the row it returns (dev: a task that is merged or cancelled, a plan that is finished or cancelled); the channel knows no state name.
  • loop: the object reached the same state loopAfter times with no wait or end in between, counted from the state changes the channel saw since it started. It is sent once for that stretch; a wait or an end starts the count again.

Every other state change, a running flip, and waiting turning off send nothing, and a row equal to the last one sent for that object (state, waiting and running) is not sent again. The last row sent for each object is kept in a file in the operad home (mcp-channel-<hash of the store root>.json), written when a block is delivered, so a change seen again after a reconnect or restart stays quiet. An object first seen after the starting read has the previous state new. An object that can no longer be found is forgotten.

The setting is in the home config.json, and is read when the server starts:

{ "mcp": { "channel": { "notify": ["waiting", "ended", "loop"], "loopAfter": 3 } } }

Leaving the key out gives the values above. Adding "changes" to notify also sends every state change, with reason changes unless it is also a wait, an end or a loop. An entry that is not waiting, ended, loop or changes is a config error that names it; loopAfter is an integer of 2 or more.

The server sends nothing until the client has sent notifications/initialized. It keeps comparing rows meanwhile, then sends the changes it saw since the start, in order.

Each notification is the server's notifications/claude/channel method with these parameters:

{
  "content": "T-0014-kernel running -> waiting: review passed",
  "meta": {
    "id": "T-0014-kernel",
    "type": "task",
    "state": "waiting",
    "previous": "running",
    "waiting": "true",
    "running": "false",
    "reason": "waiting",
    "step": "review"
  }
}

reason says why the block was sent: waiting, ended, loop, or changes. step is the last step of the object's active run and is absent when the object has none, so a block reads state="review" step="verify" when verify failed inside the review state.

content is one line, <id> <old state> -> <new state>, with : <note> appended when the row has a note. Every meta value is a string. The channel is one-way: there is no reply tool, and show, section, pending, history and the other read tools give the details.

--types <t,…> limits the channel to the named object types, separated by commas; the default is every type with views. A name that is not a type with views is a usage error that names it. The flag does not change the read tools.

Claude Code enables the extension with its development-channel flag, naming the server from .mcp.json:

claude --dangerously-load-development-channels server:operad

Lead permissions#

The server may run only the actions mcp.actions names; every other action is the owner's, and show lists it under ownerActions instead. An action that carries confirm: true also needs mcp.confirmActions to name it. The settings are in config.json and are read when operad mcp starts:

KeyTypeDefaultAllowed valuesWhen it takes effect
mcpobjectsee the keys belowchannel, actions, confirmActionsWhen operad mcp starts.
mcp.actionsarray of strings[] (operad init writes the five dev lead actions and chat:close into a new file)plugin:action namesWhen operad mcp starts: the actions the lead may run. Any other action is refused with a message naming it and saying the owner runs it.
mcp.confirmActionsarray of strings[] (operad init writes ["chat:close"] into a new file)plugin:action namesWhen operad mcp starts: the allowed actions that also carry confirm: true. An action that is only in actions and asks to confirm is refused; one only in this list is refused too.
mcp.channelobjectsee the two keys belownotify, loopAfterWhen operad mcp --claude-channel starts.
mcp.channel.notifyarray of strings["waiting", "ended", "loop"]waiting, ended, loop, changesWhen the channel starts: what sends a block. waiting is a wait opening; ended a final state; loop the same state reached loopAfter times with no wait or end between; changes every state change. An unknown value is a config error naming it.
mcp.channel.loopAfterinteger3A whole number from 2When the channel starts: how many times in a row an object reaches the same state before a loop block. A value below 2 is a config error naming it.

mcp.actions and mcp.confirmActions never change an action already running. The MCP server never offers the owner's actions as its own; show lists them separately so the lead can tell the owner what to run.

With no mcp.actions in config.json the lead may run no action. A home made before operad init wrote these lists may lack them; add the lines from config.json to its mcp section and restart operad mcp. Enabling a plugin later does not add its actions; list them by hand.

Tools#

ToolRequired argumentsWhat it returns
typesnone{ "types": [...] }, the same list as GET /v1/types.
listnone; one of type, root, parent is needed{ "rows": [...], "next": "<c>" }, the same page as GET /v1/objects.
showidThe object with its row, sections, allowed actions and ownerActions.
sectionid, section{ "markdown", "next", "mark", "tail", "delta" }, the same read as the HTTP section call; optional cursor, after, full.
pendingnone{ "items": [...] }, with only the actions the lead may run.
answerrunId, waitId, choice{ "runId", "waitId", "choice" }; optional note, confirmed.
runningnone{ "items": [...], "load": { "load1", "cores" } }.
historyid{ "id", "markdown", "next" }, the History section.
commandplugin, verbThe plugin verb's value, the same as operad <plugin> <verb>; optional args and input.
actactionThe action record; optional id, args, note.

The rest of this page gives each tool's full input schema and the result shape.

The tool table is exported as TOOLS from @operad-io/mcp; the server serves that same table. Every result is a normal MCP tool result with structuredContent and one text block whose text is the same content as Markdown. structuredContent is always an object: a list is wrapped as { "items": [...] }. next, when present, is a cursor the caller passes back unchanged.

types#

Input: { "type": "object", "additionalProperties": false, "properties": {} }.

Result: { "types": [...] }, the same listing GET /v1/types serves: each object type with views, its title, its plugin, its filters and defaultFilter when it has any, and the parents an action that creates it works on. A plugin that declares objectsUnderSettings (a bot) marks every one of its types "settings": true: clients give it no tab and list its top-level objects under settings. The Markdown is a table of type, title, plugin, whether it is under settings, filters and parents.

list#

Input:

{
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "type": { "type": "string", "minLength": 1, "description": "An object type, such as task. Optional with root or parent: then every type is listed." },
    "root": { "type": "boolean", "description": "Only rows with no parent." },
    "parent": { "type": "string", "minLength": 1, "description": "Only rows whose parent is this object id." },
    "cursor": { "type": "string", "description": "The next cursor from an earlier list." }
  }
}

Result: { "rows": [ ... ], "next": "<cursor>" }. rows are the rows of one object type, with the plugin's id, title, state and optional note and scope, plus the kernel's waiting and running flags. An error row also has error. The Markdown is a table of id, state, title, note and flags. An unknown type is a tool error with the view's message.

root and parent list one level, as Levels describes: with a type the rows of that type, without one the rows of all types in the types' order. The type's default filter applies in the level and hidden counts the rows it left out. A parent that names no object gives an empty list. A call with no type, root or parent is a tool error. A row's parent, when it has one, is in the structured row and in the show Markdown.

show#

Input:

{
  "type": "object",
  "required": ["id"],
  "additionalProperties": false,
  "properties": {
    "id": { "type": "string", "minLength": 1, "description": "A bare id or type:id." }
  }
}

Result: the object { "id", "type", "link", "row", "sections", "actions", "ownerActions" }. row is the list row. sections is the section directory. actions are the available actions the lead may run now, each with its name, on, args JSON Schema, note field name, noteRequired and confirm. ownerActions holds only the names of the available actions the lead may not run, including a confirm: true action that mcp.confirmActions does not name. The Markdown shows the row, the section directory, the allowed actions with their arguments, and an Owner actions list. An unknown id is a tool error with the view's message.

section#

Input:

{
  "type": "object",
  "required": ["id", "section"],
  "additionalProperties": false,
  "properties": {
    "id": { "type": "string", "minLength": 1, "description": "A bare id or type:id." },
    "section": { "type": "string", "minLength": 1, "description": "A section id from show." },
    "cursor": { "type": "string", "description": "The next cursor from an earlier read." },
    "after": { "type": "string", "description": "A mark from an earlier read: return only the finished content after it. The answer says in `delta` whether it is that part alone or a whole page." },
    "full": { "type": "boolean", "description": "Return the whole section without the size cap." }
  }
}

Result: { "markdown": "...", "next": "<cursor>", "mark": "<mark>", "tail": "..." }. mark is an opaque position the finished content goes to, and tail is the Markdown of the part still changing; a plugin that does not use them sends neither. With after=<mark> from an earlier read, markdown holds only the finished content after that mark, and delta says whether it is that part alone (true) or a whole page the client must replace (false). The size cap covers markdown and tail together but never cuts tail: when both do not fit, markdown is shortened first; when even the tail and the truncation note do not fit, the call is refused with an over-cap message naming --full. The text block is the Markdown, with a final line naming next when the section is paged. An unknown id or section, or a mark from another section or object, is a tool error with the view's message.

pending#

Input:

{
  "type": "object",
  "additionalProperties": false,
  "properties": {}
}

Result: { "items": [...] }, the same list as operad pending and GET /v1/pending, with only the actions the lead may run now. A question carries waitId. Each item that is about an object carries its row, as in GET /v1/pending. An action outside mcp.actions, or a confirm: true action that mcp.confirmActions does not name, is left out of both the structured content and the Markdown. The Markdown lists each pending item, its prompt, choices and actions. Call show on the item's object to see the owner actions.

answer#

Input:

{
  "type": "object",
  "required": ["runId", "waitId", "choice"],
  "additionalProperties": false,
  "properties": {
    "runId": { "type": "string", "minLength": 1, "description": "The pending item's runId." },
    "waitId": { "type": "string", "minLength": 1, "description": "The pending item's waitId." },
    "choice": { "type": "string", "minLength": 1, "description": "One of the item's choices." },
    "note": { "type": "string", "description": "The note, when the question asks for one." },
    "confirmed": { "type": "boolean", "description": "Set when the answer is a choice whose action asks to confirm." }
  }
}

Result: { "runId", "waitId", "choice" }, plus note when one was given. It records the actor { "via": "mcp", "id": "lead" }. A question that is already closed, or a choice the question does not offer, is a tool error with the view's message. When every choice is also an action on the item's object (a dev wait), the choice runs through that action, so its confirmation and the mcp.actions allow list still apply, and the result is the action record. A confirmed action needs "confirmed": true.

running#

Input:

{
  "type": "object",
  "additionalProperties": false,
  "properties": {}
}

Result: { "items": [...] }, the same list as operad running and GET /v1/running. The Markdown is a table of each active run: its object, title, flow, step, step time and run age. Each item also has object, title, stepStartedAt, stepElapsedMs and mark (the object's row mark, left out when it has none; see GET /v1/running in the manual).

history#

Input:

{
  "type": "object",
  "required": ["id"],
  "additionalProperties": false,
  "properties": {
    "id": { "type": "string", "minLength": 1, "description": "A bare id or type:id." }
  }
}

Result: { "id": "<the id as given>", "markdown": "...", "next": "<cursor>" }. The Markdown is the kernel's History section for the object. An unknown id is a tool error with the view's message.

command#

Input:

{
  "type": "object",
  "required": ["plugin", "verb"],
  "additionalProperties": false,
  "properties": {
    "plugin": { "type": "string", "minLength": 1, "description": "A loaded plugin name, such as dev." },
    "verb": { "type": "string", "minLength": 1, "description": "A verb the plugin declares, such as plan." },
    "args": { "type": "array", "items": { "type": "string" }, "description": "The command-line arguments after the verb." },
    "input": { "type": "string", "description": "The text the CLI reads from stdin, such as a brief." }
  }
}

Result: the plugin verb's output, the same value operad <plugin> <verb> prints. A value that is an object is the structured content as it is; any other value (a list, a string) is wrapped as { "value": ... }. The call builds the CLI's [plugin, verb, ...args], with input standing in for stdin, so dev plan add and dev task add take their brief from it. It resolves the pair against the loaded plugins, so a plugin verb runs even when its name matches a kernel command. A plugin whose name is itself a kernel verb is refused, even when the pair resolves to one of its commands. A kernel verb the named plugin does not declare (serve, init, plugin ..., secret ..., http ..., and the other commands the CLI owns), and any other verb it does not declare, is refused with a tool error.

act#

Input:

{
  "type": "object",
  "required": ["action"],
  "additionalProperties": false,
  "properties": {
    "action": { "type": "string", "minLength": 1, "description": "A <plugin>:<action> name from show." },
    "id": { "type": "string", "description": "The object id when the action targets one." },
    "args": { "type": "object", "description": "The action's arguments, as its schema names them." },
    "note": { "type": "string", "description": "The note for an action whose schema declares one." }
  }
}

Result: the same action record POST /v1/act returns, with plugin, action, name and value. It runs through views.act, records the actor { "via": "mcp", "id": "lead" }, and records a person's answer for a run that waits. An action not named in mcp.actions is a tool error naming it and saying the owner runs it. An action with confirm: true is refused the same way unless mcp.confirmActions also names it.

Errors#

A JSON-RPC error is used for a malformed request, not for a view refusal:

CodeWhen
-32700The line is not JSON.
-32600The message is not a JSON-RPC 2.0 request.
-32601The method is not one of the methods above.
-32602tools/call is malformed: an unknown tool, no name, non-object arguments, or arguments that do not match the tool's input schema.
-32603An unexpected error happened while reading a view; the message is generic.

A view refusal is a successful tools/call response whose result has "isError": true and one text block with the view's own message. This covers an unknown id, section or type. A tool error carries no structuredContent. The server writes no stack trace and no internal name.

Example:

{"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"no object \"task:nope\""}],"isError":true}}
