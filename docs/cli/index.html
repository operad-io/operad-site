The command line

operad help prints the command table; this page says what each command does, which options it takes and what it prints. The commands of the dev plugin are also on its page; the terminal client is on its page, pair on the app page, mcp on the MCP page, and the environment variables on the environment page.

Why it exists#

operad is the one way to reach a home from a terminal, a script or an agent: set it up, start serve, see what is pending, answer it, and run the commands the plugins declare. The CLI does not hard-code what a plugin can do. A plugin declares its object types, actions and verbs, and the CLI builds operad <plugin>:<action> and its flags from that declaration, so a new plugin is usable from the command line without a change to the CLI. Most commands read and write the home directly, so they work whether or not serve is running; serve is the process that carries runs forward, and the CLI never does that work itself.

How it works#

  1. The command finds the home: $OPERAD_HOME, otherwise ~/.operad. It opens the store and loads the plugins that config.json enables. Nothing needs to be running for this.
  2. It routes the words. A kernel command (pending, list, show, history, settings, plugin, secret, trigger and the rest of the Commands table) is handled by the CLI. <plugin>:<action> <id> runs an action on an object; <plugin> <verb> runs a verb that plugin declares, and the bare <verb> works when only one plugin declares it. See Actions.
  3. A read command prints rows and sections that the plugins produced. Output is text for a terminal, or JSON with --json; see Filtering a list and The History section.
  4. A command that changes something, such as an action or an answer to a pending item, records it in the home. A running serve picks the record up and continues the steps the run asks for. With no serve, an answer prints recorded; it runs when operad serve is running.
  5. operad serve takes the home lock (serve.lock) before it opens the store or the port, so a second serve for the same home exits with code 4 and changes nothing. operad serve stop signals the process named in that lock; see Stopping serve.
  6. Every command ends with one of the exit codes, so a script can tell an error (1) from a usage mistake (2) and from a state that does not allow the command (3).

Exit codes#

CodeMeaning
0The command did what it was asked, or had nothing to do.
1An error: a bad id, a config or plugin that does not load, a refused check, an editor that failed.
2A usage error: an unknown command or option, a missing argument, a bad value. operad help is printed after the message.
3The state does not allow it: a plugin is disabled, a run is active, a task phase does not allow the change, a serve did not stop in time.
4Another process holds the home lock, or a second serve for the same home.
141The reader closed the pipe (128 + SIGPIPE). Later output is dropped.

The flags of an action are made from its arguments: an argument named note becomes --note <text>, a boolean becomes --flag or --flag=true, and an array or object takes JSON. An action that declares creates is not offered on a parent's page; it is run from the new-object entry or the command line.

Stopping serve#

operad serve stop [--timeout <secs>] stops the serve of the current OPERAD_HOME. It reads serve.lock:

  • With no lock, or a lock whose process is gone, it prints no operad serve runs for <home> and exits 0. It signals nothing and does not delete a stale lock; the next serve replaces it.
  • With a live process it first checks that the process is a serve: it asks the OS for the process's command line (ps -p <pid> -o command=, the same on macOS and Linux) and requires serve as a word of it. The lock alone is not enough, because a PID can be reused after a serve died. When the process is not a serve the command prints an error naming the PID, signals nothing and exits 3.
  • Otherwise it sends SIGTERM, the stop serve already handles, prints stopping operad serve (pid <pid>), waits until the process is gone or the lock is released, prints stopped and exits 0. It never sends SIGKILL.

--timeout <secs> is how long it waits: a whole number of seconds, at least 1, default 30. If the serve is still running after that, it prints an error that it did not stop, with kill -9 <pid> as the way to force it, and exits 3. A --timeout of 0, one with no value, or one that is not a whole number, is a usage error (exit 2). operad serve with no subcommand runs the loop as before.

What happens to running work: SIGTERM ends the loop after its current pass, then serve stops the notifier, the HTTP server and the trigger sources, releases the lock and exits. It does not kill a step. A step that is running in its own process when serve stops keeps running, and the next serve for the home picks the run up again. Nothing starts new work or advances waits and timers while no serve runs; operad serve or operad tui resumes it.

A step cleans up after itself: when it ends, every process it started that is still running (a loop a worker left in the background, for example) is stopped, and the step's log lists them. At start, serve does the same for the steps of runs that are no longer active. See "What a step cleans up" in packages/dev/REFERENCE.md for how processes are found and what it cannot find.

A restart does not disturb a check or command that is running. Each run is a process of its own, and the command a step starts is held by that run, not by serve: stopping and starting serve sends no signal to it, does not stop its line and does not run it a second time. The command ends on its own, and the run records its exit code as if nothing had happened. Only the death of the run's own process stops its command (and the next serve then starts the step again).

Changed code#

serve and each run's process keep running the code they loaded only until the files change. serve watches the kernel's code (engine, cli), each loaded plugin's package (source, flows, schemas) and the workspace packages that package depends on. After the files have been quiet for a second it starts a fresh process to check that the new code loads. If it does, serve stops the way operad serve stop does, prints reloading: <what changed> and starts again from the same command line and environment, under the process you started (it stays in your terminal, passes Ctrl-C on, and ends with the serve's exit code). A step that is running keeps the code it started with and finishes; a run's process looks at the files between steps, and when they changed it stops so that a new process takes the next step. operad history shows one line, continuing on updated code, for that.

New code that does not load (a syntax error, an invalid schema) takes nothing down. serve keeps running the old code and prints code changed (...) but does not load; the old code keeps running: <problems> on its error output; it reloads when the files load again, also when it was a settings file (config.json, triggers.json, keys.json) that did not read and was fixed. A run's process does not take its next step on code that does not load: it prints the same line into the run's log (<store>/logs/runs/<run id>.out) and waits for the files to load. Settings files are read again at their next use; a change to them alone does not restart serve.

While serve runs older code than the files on disk, operad pending shows one item: serve runs older code than the files on disk: restart serve to load them (operad serve stop, then operad serve). It appears when the new code does not load (see above), or when the restart could not listen on its addresses and the old code serves again. It has no actions, and it leaves when serve runs the code on disk again: after the files load and serve reloads, or after you restart it, or when the files go back to what serve loaded.

When the restart could not listen and the old code serves again, that serve does not try the same change again. What it still runs from before is operad itself and the plugins given by package name (and the files a path plugin imports), so a change to those leaves the item above showing. A plugin given as a path, and a plugin enabled since serve first started, are loaded again from the files on disk, so a change to those alone shows nothing. The next different change goes through the load check and reloads as usual.

The History section#

Every object has a History section (operad show <id> --section history, the last tab in the web page and the terminal screen). It groups by run, then by attempt of each step. A run's heading names the flow and when it started; the run id comes once at the end of the run's block, in small text, for support. A step attempt is one line: the local time of the host that serves it, the step, the attempt when it is above 1, why it started when that is not the plain next step (after fail, after reverify), the outcome, how long it took (a running step shows running and how long so far) and the outcome's detail cut to one line with …. People's answers and events keep their own line. A date line starts each new day.

## dev run · started 21:38
**2026-11-08**
- 21:38:41  worktree  ready  1s
- 21:38:44  work  done  41m
- 22:20:01  review  fail  58s  packages/dev/src/gate.ts:1059 major …
- 22:21:01  work  attempt 2  after fail  done  1m
- 22:22:02  confirm  reverify  8m
- 22:30:02  you chose merge: via plugin, as dev
- 22:30:04  verify  after reverify  running  2m

operad show <id> --section history --full keeps each detail whole. operad history <id> prints every step with a UTC time; --json prints one object per step, or one object per run when the id names several runs.

Levels#

A plugin can arrange its objects in levels. A row may carry parent: the id of the object one level up, either a full id (plan:repo/P-0001) or a bare id that resolves the way operad show resolves it. The kernel passes it through and never makes one up. A row without parent is at the top level.

  • operad list <type> --root lists the rows of that type with no parent; operad list <type> --parent <id> lists the rows whose parent is that object. Plain operad list <type> stays flat.
  • GET /v1/objects?root and GET /v1/objects?parent=<id> do the same. type is optional with them. Without type they list across the types of all plugins in a stable order: the types in the order GET /v1/types gives them (plugin load order, then the order each plugin declares its types), and within a type the rows in the order a plain list of that type has (by id). next pages through that whole order. root and parent cannot be used together.
  • The type's filters apply inside the level: a request with type uses the named filter or the type's default; without type each type uses its own default (or the named filter, where the type has it). hidden counts the rows of that level the filters left out.
  • A parent that names no object is not an error: the list is empty. A row whose parent names an object that does not exist still lists under parent=<that id>, and not under root.
  • operad show <id> prints parent: <id> under the row when it has one.
  • The MCP list tool takes root and parent too; see the MCP page.

Filtering a list#

A plugin can give an object type filters, so a list does not show every old object. In the plugin, the object type has an optional filters field, an ordered list of { "name": string, "states": string[], "default"?: boolean }:

objects: [
  {
    name: "task",
    filters: [
      { name: "active", states: ["proposed", "ready", "running"], default: true },
      { name: "done", states: ["merged"] },
    ],
  },
],

A filter is data: a row matches when its state is one of states. A row whose state is error (its view failed) is shown by every filter, so a broken row is never hidden. At most one filter has default: true; with none marked, the first is the default. Loading the plugin refuses an empty or duplicate name, two defaults, an empty states, and the name all, and names the field.

The kernel adds the filter all, which tests no state, right after the default. The tasks above list as active, all, done.

operad list <type> [--filter <name>] [--repo <name>] uses the type's default filter when it has one and --filter is not given. --filter all lists everything. When the filter left rows out, the last line is N hidden (--filter all to show). --repo keeps the objects of one repository, and works together with --filter. A type without filters refuses --filter with "this type has no filters". The HTTP interface takes the same choice as filter (see the endpoints below).

The dev plugin declares these filters (all follows active):

TypeFilterStates
taskactive (default)proposed, ready, running, review, integrating, waiting, paused
taskdonemerged
taskcancelledcancelled
planactive (default)draft, confirmed, paused
plandonefinished

The chat plugin declares open (default) and closed; all follows open. The bot plugin declares open (default) and removed; all follows open. The bot proposal type declares pending (default), applied and rejected.

Actions#

An action is run as <plugin>:<action> <id>, or as <plugin> <action> <id>, or as <action> <id> when only one plugin offers that action. The command line builds one flag per argument the action declares:

operad dev:reject T-0003 --note "cover concurrent writers"
operad dev confirm T-0003 --yes
operad chat:send C-0001 --note "why does the gate fail on main?"
operad dev:model C-0001 --model sonnet

A required note with no --note is asked for in a terminal, and refused in a pipe; a confirm: true action asks [y/N], and --yes skips the question. The action's record is printed when it returns a value. An action that opens an object (opens) only prints its line; the terminal and the app open the object. An action that records an answer prints recorded; it runs when operad serve is running when no serve holds the home.

dev commands#

operad dev repo add <path> [--name <name>] registers a directory that is a git work tree with a remote. It refuses, and writes nothing, a directory that is not the root of a git work tree, that has no remote, or that is already registered, and prints the reason. It writes .operad/dev.json when the repository has none. operad init checks, for each registered repository, that its remote can be reached and has the main branch published; it asks the remote read-only and pushes nothing. operad dev repo list prints no repositories or one <name> <path> line per repository. operad dev repo remove <name> prints removed <name>. It refuses a repository that has an open task (repository "<name>" has <n> open task(s)); merge or cancel those tasks first.

operad dev plan add --slug <slug> --title <title> [--concurrency <n>] [--flow <name>] [--repo <name>] creates a plan and prints its id. The request is read from stdin when there is any. --concurrency is a whole number from 1 to 16 and defaults to 1 when it is left out.

operad dev task add --plan <plan> --slug <slug> --title <title> [--after <task>]… [--area <area>] [--flow <name>] [--repo <name>] [--chat <id>] creates a task in the named plan and prints its id. The brief is read from stdin when there is any. --after may be repeated; the task waits until each named task is merged. A task of another repository is named <repository>/<task id>. A task cannot follow itself or close a cycle. --chat uses the worktree that chat asked for.

operad dev task edit <id> [--repo <name>] replaces the brief of a proposed or ready task. The new brief is the text on stdin when it is not a terminal and carries some, otherwise what you save in $EDITOR (or $VISUAL when EDITOR is unset). With no editor and no input the command fails and says so. It prints the task id.

operad dev task update <id> [--title <title>] [--after <task>]… [--area <area>] [--flow <name>] [--repo <name>] changes a task and prints its id. --after "" clears the tasks it waits for; --area "" clears the area. The flow can change only before the first attempt; after that the command refuses.

operad dev start <task> [--repo <name>] asks for a ready task to start and prints start requested for <id>; the next serve pass claims it.

operad dev reruns prints one line per test that passed only on a rerun: <count> <test name> <task id>; it prints no test has passed on a rerun yet when there is none.

The short forms operad repo …, operad plan …, operad task …, operad start … and operad reruns work because only dev declares those verbs.

bot commands#

operad bot skill <bot> <name> [--from <dir>] proposes a new or changed skill. Without --from, stdin is a JSON object with skill_md and files; with it, the directory's files are read. The skill needs a SKILL.md. Nothing is written until a person approves the proposal in pending.

operad bot mcp <bot> <name> <command> [args…] starts a local MCP server once, reads its tool list, and proposes registering it. With no command, stdin is a pasted mcpServers entry. A package command (npx, bunx, uvx, pipx) must name an exact version, as name@1.2.3; a tag or range is refused before the server starts. A remote server (an address) cannot be registered yet.

operad bot setting <bot> reads a JSON object from stdin and proposes the change. A bot can tighten the default access profile, never loosen it. MCP servers are not changed here; use bot mcp.
