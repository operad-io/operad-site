config.json

config.json configures operad. This page says where the home is, every key of the file, and every plugin's settings section. The http keys are also on the HTTP page, the notify keys on notifications, the mcp keys on the MCP page, and the repository settings of dev on the dev page.

Why it exists#

Operad needs one place to keep what a person has set up: which plugins are installed, where the store is and which interfaces are on. That place is the home directory and its config.json. The file is written by operad init when the home has none, and changed afterwards by hand or with operad plugin enable and operad plugin disable. Operad does not rewrite a home that already has a config.json, and it keeps no hidden defaults for the file that operad init writes.

How it works#

  1. A command finds the home: $OPERAD_HOME when it is set and not blank, otherwise ~/.operad. It reads config.json there; with no file, there are no plugins.
  2. The kernel reads only the keys it names: plugins, store, http, notify, mcp and ask. A wrong value in one of them refuses the file with one line; an unknown key is ignored.
  3. For every entry in plugins that is not disabled with "enabled": false, the kernel imports its module (the key's name when module is not given) and checks the entry's settings with that plugin's own schema.
  4. A plugin that does not import, has invalid settings or declares another name does not load. The rest still load, and serve and operad plugin check print the line that says why.
  5. A disabled plugin is not imported; its stored objects stay.
  6. A one-shot command reads the file again on its next run. A running serve watches the file and reloads when the new file loads; when it does not load, the old configuration keeps running and the problem is logged. A step that has already started keeps the settings it started with.

The keys are in The sections and each plugin's settings in Plugin settings.

The home#

operad keeps its state in one directory: $OPERAD_HOME when it is set, and ~/.operad otherwise. The home holds config.json, the store, the secrets directory, access-user.json, keys.json, triggers.json, tui.json and the themes directory. A secret file is mode 0600 inside a 0700 directory; nothing in this manual prints a secret.

    "bot": {

            "model": "opencode-go/deepseek-v4.1-flash",

            "speaker": "Assistant",
            "mcpAllow": ["notes.search"],
            "access": { "readOnly": true, "askCommands": ["git push"] }
          }
        }
      }
    },
    "claude": {
      "module": "@operad-io/harness-claude",
      "settings": {
        "model": "sonnet",
        "effort": "high",
        "command": "claude",

      }
    },
    "pi": {
      "module": "@operad-io/harness-pi",
      "settings": {
        "model": "opencode-go/deepseek-v4.1-flash",
        "models": ["opencode-go/deepseek-v4.1-flash", "openai/gpt-5"],
        "thinkingLevel": "medium",

      }
    },
    "radian": {
      "module": "@operad-io/harness-radian",
      "settings": {
        "command": "radian",
        "wallTimeSecs": 300,
        "stallSecs": 600,
        "concurrency": { "anthropic/claude-sonnet-4": 1 }
      }
    }
  },
  "store": { "backend": "sqlite", "path": "store/log.sqlite" },
  "http": { "enabled": true, "port": 7480, "listen": ["127.0.0.1"] },
  "notify": { "command": "sh ~/.operad/notify.sh", "on": ["waiting"] },
  "mcp": {
    "channel": { "notify": ["waiting", "ended", "loop"], "loopAfter": 3 },
    "actions": ["dev:rework", "dev:reverify", "dev:reject", "dev:priority", "dev:concurrency", "chat:close"],

}

operad init writes a config.json when the home has none: shell, radian, chat and dev installed, the store at store/log.sqlite, http on at 127.0.0.1:7480, notifications off, the mcp.actions and mcp.confirmActions lists above and the ask grace of 600 seconds. All of it is written into the file; nothing in it is a hidden default. A home with no config.json at all has no plugins and allows no lead action.

An existing home is never rewritten. operad init on a home that has a config.json keeps the file as it is; the one exception is a file with no plugins key, which gets the default plugins added and nothing else. A config.json without mcp.actions allows no lead action. A home made before this change lists its plugins already but may have no mcp.actions; to keep the lead's actions, add these lines to its mcp section and restart operad mcp:

"mcp": {
  "actions": ["dev:rework", "dev:reverify", "dev:reject", "dev:priority", "dev:concurrency", "chat:close"],
  "confirmActions": ["chat:close"]
}

Enabling a plugin later does not add its actions to mcp.actions; add them by hand.

Every top-level section is optional. The kernel reads only the keys it names: an unknown key at the top level, inside an engine section (store, http, notify, mcp, ask) or inside a plugins entry is ignored. The one place a typo is refused is plugins.<name>.settings, which is checked by that plugin's own schema; an unknown key there refuses the plugin with one line naming the plugin and the field.

Plugin settings#

Plugin settings sit under plugins.<name>.settings. A plugin with no settings schema has no keys: shell and the cron source (cron, the @operad-io/source-cron package) are configured entirely by their flow steps and by triggers.json. review-grading is a library that reads <repository>/.operad/review.json, documented on the dev page. The MCP server, the terminal client, the HTTP interface and notifications are configured by the sections above, not by plugin settings.

Every setting is read when the plugin loads. A running serve reloads when config.json changes and the new file loads; a step that has already started keeps the settings it started with. The exceptions are named in each table.

bot#

The bot section describes chats that belong to a bot. The default bot default exists even when it is not written. Names are lowercase letters, digits, - and _, and start with a letter or digit; any other name refuses the bot with bot "<name>": a name is lowercase letters, digits, "-" and "_", and starts with a letter or digit. A bot is read again at every reply, so an edit applies to the next reply. See Chats and bots.

triggers.json#

triggers.json in the home holds the rules that say which event starts which flow. It is a JSON array; a missing file means no rules of your own. A rule of yours replaces a plugin rule with the same source and type; a plugin rule for that pair is then not used.

[
  {
    "source": "operad",
    "type": "dev.waiting",
    "start": { "flow": "dev", "params": {} },
    "object": "$event.object",
    "mode": "observe"
  },
  {
    "source": "cron",
    "type": "tick",
    "start": { "flow": "nightly" },
    "object": "flow:nightly",
    "mode": "auto",
    "schedule": "0 3 * * *"
  }
]

The cron source is the plugin named cron from @operad-io/source-cron. It emits one tick per due minute for each rule with source cron and a schedule; other rules ignore schedule. A rule may not name the reserved source operad when it is added by a command.

If triggers.json is not valid, the whole file is refused, with the rule and field in the message. operad serve logs it and runs without sources until the file is fixed; a command that needs a rule reports it. A running serve watches the file and reloads when the new file loads.

Settings from a client#

operad settings lists the settings a person may tune and operad settings set <name> <value> changes one; --repo <name> names a registered repository. A global setting is <plugin>.<path>. A project file whose name equals its plugin's name takes the plugin name alone, so .operad/dev.json is dev.concurrency, dev.autoDefault, dev.gate.commands, dev.gate.commandTimeoutSecs, dev.reviewer.use, dev.reviewer.args, dev.reviewer.timeoutSecs and dev.reviewer.fixLevel. Another file adds its name: .operad/review.json is dev.review.default.levels, dev.review.default.rules and dev.review.default.fixLevel. Changing what merges (autoDefault, a fixLevel, the levels and rules) asks for --yes.
