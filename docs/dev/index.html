dev.json and the dev plugin

The dev plugin runs plans and tasks on a repository. Its project settings are in .operad/dev.json; its commands and what they do are in the sections below. The settings a client may change are in config.json.

How a task goes from request to merge#

A request becomes a plan, a plan holds tasks, and each task runs through the same path. You are in the loop at two points: when you confirm the plan, and at the merge.

plan -> tasks (draft) -> confirm -> ready -> work -> check -> review -> you merge -> main
                                               ^       |        |
                                               +-------+--------+  rework
  1. Plan and tasks. A plan is one request (operad plan add). Each task in it has a brief, the instructions for the worker (operad task add). A task may wait for another with --after. operad dev:confirm <plan> moves the plan's draft tasks to ready; a confirmed plan is what operad serve schedules.
  2. Start. serve starts ready tasks, up to the repository's concurrency and each pool's cap. Each task gets its own git worktree and branch, so tasks never touch each other or your checkout.
  3. Work. A worker, chosen from workers through a pool, runs in the task's worktree with the brief and commits there. A worker whose model is unavailable can hand the work to its fallback.
  4. Check. The commands in gate.commands run against the commit. A failing test is run again on its own first, so a flaky test is told apart from a real failure.
  5. Review. The reviewer reads the change and writes a report. Findings that reach reviewer.fixLevel (default major) fail the review.
  6. Rework. A failed check or a failed review sends the task back to the worker, up to maxAutoRework times (default 2). After that the task waits for you.
  7. Waiting for you. A task that passed check and review waits in operad pending as ready to merge, with the actions dev:merge, dev:reject, dev:rework, dev:reverify and dev:cancel. A task also waits when something needs a person: review findings, a failed gate, the rework limit, a worker that added no commit.
  8. Merge and clean up. dev:merge puts the verified commit on main (integration.style), runs integration.keyCommands, and pushes to the remote. Then cleanup removes the task's worktrees and branches. Tasks of one repository integrate one at a time. If the remote refuses the push, nothing is written and the task waits with a note.

Every step is recorded: operad history <task> shows what ran, what a check or review found, and what you chose. A run whose process died starts again from its last recorded step. A plan can go further without you: operad dev:auto <plan> --level merge merges reviewed work after the check passes, --level run starts the plan's tasks without you and still stops each one for you at the merge, and --level off waits for you at every start and merge. autoDefault sets the level for new plans.

The keys for each part are in the sections below: the repository and its workers, the gate and its checks, work, review, integration and cleanup and flows and their stages.

Every .operad/dev.json key#

A repository's dev.json is JSON; the schema is packages/dev/dev.schema.json. A missing file means the defaults below. The file is read again by every step and every scheduler pass; when it stops being valid, the last valid settings stay in force and operad pending shows one item for the repository (see When dev.json is not valid). A wrong value is refused with the field path in front, such as workers.claude.fallback: ....

{name} is replaced by the shell-quoted test name and {pattern} by the shell-quoted anchored regular expression of it. In stress, {file} is the shell-quoted test file, or nothing when dev does not know it. A check that uses failed does not use check.rerun for that line.

When a test passes only on its rerun often enough (check.flakyTask), the brief of the task dev proposes uses the failed settings of the line whose match found the failure: the excerpt is the line match found and the lines before it (the first match in the log); stress gives the "Reproduce it" command, and with it the brief asks for the number of runs in place of <N>; rule names a file whose text is the repository's rule for flaky tests. Without stress the brief has no command. Without rule, or when the file is missing or empty, the brief says: "A test that failed and then passed on rerun is a bug until shown otherwise. Do not raise a timeout or add a retry inside a test to make it pass." The task has no area. See Checking a change.

A check that failed only because tests ran to their timeout normally waits for a quiet machine, runs again, and waits for a person if it happens twice. There is one exception: when the failed test was run alone (its failed.rerun command), timed out again, and the load during that run was below check.flakyLoadLimit (by default twice the number of cores), the machine is not to blame. The change goes back to the worker as a failure whose note names the test, says it "timed out at 30 s when run alone under load 3 on 10 cores", and gives the log path. A timeout seen only under a load above the limit, or a test that passes when run alone, is handled as before.

review.json#

Why review.json exists#

A reviewer reports findings, and each finding has a severity: critical, major or minor. A review fails when a finding reaches a chosen level. review.json is where a repository writes down what the three levels mean, which extra rules the reviewer grades by, and the lowest level that fails a review, for one flow or for all of them. It does not change what the reviewer is asked to look at, and it does not start a review; the dev plugin reads it when a review needs it. A repository without the file gets no grading text, and dev.reviewer.fixLevel (default major) sets the level.

How review.json grading works#

  1. A review stage names its entry with grading; when it names none, the entry is the flow's own name. The entry is merged over default field by field: levels per level, rules as a whole.
  2. dev reads .operad/review.json in the repository and checks it. A file that is not valid fails the review step with the file named; no grading is guessed.
  3. The review prompt gets a "Grading" section with the levels texts and the rules, word for word, so the reviewer grades in the repository's own terms.
  4. The reviewer writes its report to a new file under .operad/review/ in the gate worktree (see where the reviewer writes its report). dev checks the report and keeps its own copy in the store.
  5. Each finding in the report has a severity. The fix level is fixLevel of the flow's entry, else of default. When neither sets one, it is the strictest of dev.reviewer.fixLevel and every fixLevel that review.json sets for any flow, so a review never grades more leniently than the repository asks anywhere.
  6. A finding counts when its severity is the fix level or above, in the order critical, major, minor.
  7. A review with no counted finding passes. One with a counted finding fails, and the failure lists each of them as <file>:<line> <severity>: <summary>; the task goes back to the worker or waits, as in the path from request to merge.
  8. A finding below the fix level does not fail the review; it is kept as a note on the task.

.operad/review.json holds the grading a reviewer reads and the lowest finding that fails a review. It falls back field by field to default. The file is read when a review step needs it; the review section explains what a reviewer does with it.

    "rules": ["Do not ask for changes the task did not ask for."],

Reverify and an attempt that adds no commit#

dev:reverify merges the current main into the task branch first, then runs verify and review again with no worker. A clean merge goes straight to verify; a conflicting main sends the task to the worker.

When the worker adds no commit, the task waits with work did nothing if the branch has nothing beyond main or its latest commit already passed verify. If the branch already holds commits not on main and its latest commit has not passed verify (an earlier run stopped before verify ended), the task does not wait: history says the branch already has unchecked work; checking it and the task goes on to verify.

Where dev commands run#

A dev command takes its repository from the directory, from --repo <name> or from a qualified id such as operad/T-0045-shell-hang-guards; a bare id outside a repository works when only one repository has it. The rules are in packages/dev/REFERENCE.md.

When the reviewer is unavailable#

A review whose harness reports a model error (unavailable or usage_limit), or whose error output says HTTP 429, does not lose the attempt. The same review round runs once on reviewer.fallback when .operad/dev.json sets one. Without a fallback, or when the fallback is unavailable too, the task waits reviewer.retrySecs (default 120 seconds; each further wait doubles, up to 30 minutes) and then runs the review again. It does not start a worker and does not count a rework. A round uses its fallback at most once, so a retry that finds the primary unavailable again waits rather than calling the fallback a second time.

A round waits at most 6 times (about 90 minutes at the default). Then the task waits for a person with the note review did not finish (model unavailable). A review that cannot fit another run in its three-hour step time does the same with review did not finish (out of time). During the wait, merge, reject, rework and reverify are not offered. A review that times out is retried once with the same arguments; a second timeout waits for a person with the note review timed out twice. A crash during a review resumes the same round and reuses the answer the reviewer already gave, so a fallback is not called twice. operad history <task> names the model that reviewed each round and why a fallback or a retry happened.

When a task waits or is stuck#

  1. operad pending: is it waiting for you? A task that needs a person stays there until you merge, reject or cancel it.
  2. operad running: is a run still moving? A run with no live process is started again by serve on its next pass.
  3. operad show <task>: read its sections, especially changes and the attempts, for the phase and the last recorded failure. operad show <task> --section brief shows the brief.
  4. operad history <task> (or operad history <run id> for one run): read the last lines for the step and the reason. A failed check or review names the command, the log file and the finding.
  5. If serve is not running, start it again with operad serve. Do not kill a run process: an interrupted run is recovered on the next pass, and a run that was not interrupted is left alone.
  6. If operad init reported a failed check, fix what it names and run it again.
  7. A task that keeps failing the same step stops for a person after repeated attempts. operad dev:cancel <task> --yes stops it for good; operad dev:reject <task> --note "what to change" sends it back to its worker.
  8. A task that waits after a failed check, or after the worker returned nothing or failed (a model 429, a check killed from outside): - operad dev:reverify <task> merges the current main into the branch, then runs the check and review again with no worker. Use it when the failure was flaky. - operad dev:rework <task> --note "what to do" writes your own ## Rework <n> (lead) into the brief and runs the worker again. Neither counts toward maxAutoRework.
  9. operad dev:pause <task> --yes stops a task for a while: it keeps its branch, commits and attempts, holds no place and is not started. operad dev:resume <task> --yes makes it ready; the next start continues on its branch.

An action needs --yes because it is your decision; in a terminal without --yes it asks first. Delete nothing by hand under .operad-worktrees: cleanup removes the task's worktrees and branches after a merge. If cleanup reports a failure, the task is still merged; remove the leftover with the command the line names.

Where the reviewer writes its report#

The reviewer runs in the task's gate worktree, and some agents (radian, for one) cannot write outside the folder they run in. So each reviewer call is told to write its report to .operad/review/<run>-attempt-<n>-review-<round>-try-<k>.json inside that worktree, a path that is new for every call (k counts the calls before it in the round). dev reads the report there, checks it, and keeps its own copy in the store under dev/reviews/<run>/; that copy is the record. dev never deletes, truncates or overwrites a file in the review workspace: it creates .operad/review when missing, and refuses to write through a link or over an existing file, failing the review with the path instead. The gate worktree is disposable and is replaced by the next gate step, which removes the reports with it. A reviewer that finishes without writing a report is shown as could not write the report with its last message; a file that fails the check is shown as wrote an invalid report.

The harness plugins: claude, codex, pi and radian#

Why they exist#

operad does not bring its own agents. It drives the ones you have installed: your claude, codex, pi and radian. The login, the updates and the quota of each stay with your installation: operad downloads no agent and signs in to none. A harness plugin lets a flow start any of them the same way, with a step named <plugin>/agent, and read one kind of result, whichever agent ran. Which agent a task gets is not the harness's choice; the flow's workers and pools make it.

How they work#

A <plugin>/agent step, in order:

  1. Starts your agent in the step's working directory (for a dev task, its worktree), through the route described below.
  2. Passes it the prompt, with the model from the step's --model argument (or the plugin's model setting, where it has one).
  3. Watches the run: it ends when the wall time (wallTimeSecs) or the silence limit (stallSecs) is reached or the step is stopped.
  4. Judges each tool call against the access profile the run was given, where the agent lets the harness see the call (see access).
  5. Writes the tool calls and messages to the step log.
  6. Reads the agent's closing result and ends done, failed or interrupted.
  7. Records what the run used in usage (see Usage and end results).

The four differ in these ways:

  • claude: runs your own claude through the Claude Agent SDK, with the login claude already has. A step is one foreground turn.
  • pi: finds the pi library you installed from the pi on PATH and loads it in a child process. It needs a pi of version 1.5.0 or newer.
  • radian: runs radian exec in the directory. radian cannot let through a one-time permission, so a profile that carries one is refused for it. It is the default dev.reviewer.use.
  • codex: starts your codex-acp and talks to it over ACP, with your Codex login. It is off until operad plugin enable codex. Codex's own sandbox stays on and limits writes to the worktree, and the access profile is asked only about what leaves the sandbox. A subscription login gives no cost, so costMicros is null.

The time limits and the per-model limit are in the sections that follow.

The claude settings#

claude runs claude, Anthropic's coding agent, instead of radian. It is not in the default config: turn it on with operad plugin enable claude.

Outside a workspace checkout, enabling installs @operad-io/harness-claude and the Agent SDK client it needs into a Bun project under ~/.operad/plugins, skipping the SDK's optional platform packages. It does not install claude itself. The first enable needs network access to the npm registry. When the package is not installed, operad plugin check claude names the command that installs it.

Install claude and log in. operad does not bring its own claude: it uses the one you installed (see https://code.claude.com), so a claude command must be on PATH. Run claude once and log in. operad uses your own login and passes no credential of its own. operad plugin check runs claude --version and claude auth status and reports the claude version, the Agent SDK version and the login kind (such as claude.ai (max)). It fails, saying what to do, when there is no claude, when claude is older than 2.1.319, or when it is not logged in. The SDK version is only reported. To use another claude, set command in the claude section of config.json to its path.

A machine without a browser. Run claude setup-token on a machine where you can sign in; it prints a token that stands for your claude subscription and lasts a year. On the machine without a browser, put it in the environment of operad serve as CLAUDE_CODE_OAUTH_TOKEN. operad hands the whole environment to claude unchanged and never reads, logs or stores the token. Treat it like a password and keep it out of config.json.

Whose subscription. operad runs your own tools on your own machine with your own claude login. Anthropic does not let a product offer claude.ai login or its rate limits to other people unless it has approved that, so a copy of operad that is shipped to others would not offer claude.ai login; it would use an API key.

Which credential is billed. claude uses an ANTHROPIC_API_KEY found in the environment before it uses your subscription login. Because operad hands the whole environment to claude, an ANTHROPIC_API_KEY set in the environment of operad serve makes claude bill that key and not the subscription. To check which one a run used, read the session line at the start of the step's log: apiKeySource is none for the subscription login and ANTHROPIC_API_KEY when that variable is set (the other values name other key sources). operad plugin check reports the login kind too; run it in the same environment as operad serve. The cost a step records is estimated for a subscription login (the price of the tokens at API rates, not what you are charged) and exact for a key.

Long commands under claude#

claude runs each step as one foreground turn. Nothing moves to the background, and the tools that only wait for background work are off, so a long command such as the gate runs to its end inside the turn. The setting bashTimeoutSecs (integer, 1 or more, default 1800) is the longest one Bash call may run, in seconds. If claude nevertheless starts a second session after it gave its result, the step ends failed with a message that says so.

Long commands under pi#

pi gives each call of pi's bash tool a time limit, so a command that never ends (a read from a FIFO nobody writes to) cannot hold a run until its wall time. The setting bashTimeoutSecs (integer, 1 or more, default 1800) is the longest one bash call may run, in seconds. It is both the default and the maximum: a call the model gives no timeout runs under it, and a timeout the model asks for above it is brought down to it. When a call reaches the limit, pi stops the command and its children and the model gets an error that says the command timed out; the run goes on, so the model can try something else. A value that is not an integer of 1 or more (0, a negative number, a string) is refused when the plugin loads, with the field path. The setting is read when a step starts, so a change takes effect with the next agent step.

The default is 1800 s (30 minutes), the same as claude, because a gate such as bash scripts/verify.sh (install, type-check and the whole test suite) runs in the foreground inside one call and must not be cut short. A project whose gate is faster can set a lower value to catch a stuck command sooner.

stallSecs is unchanged: it measures silence while no tool call is open, and an open tool call is not a stall (see packages/harness/pi/REFERENCE.md). The time limit above is what bounds a single tool call.

The agent's shell and the user's aliases#

An alias or function from the user's own shell setup, such as ls defined as eza --git --hyperlink, must not change what a command in an agent run does.

  • pi: pi runs each command as bash -c (a non-interactive shell with no rc files, so no aliases or functions). The worker also removes BASH_ENV and ENV from its environment, the two variables that make a non-interactive shell read a file.
  • radian: radian runs /bin/sh -c, which reads no user setup.
  • claude: claude's Bash tool sources a snapshot of the user's ~/.zshrc or ~/.bashrc before each command, and claude has no supported switch (environment variable or setting) that turns the snapshot off. CLAUDE_CODE_SHELL only picks which of zsh and bash is used; the snapshot is read from the home directory. operad does not work around this: a user whose rc file defines an alias that hangs (or changes the output of) a common command should guard it there, for example [[ -o interactive ]] around the alias, or define it only in a file that agents do not read. The bashTimeoutSecs limit above still stops a hung command after its time.

Sharing agents between flows: the pool plugin#

Why the pool plugin exists#

Agent runs cost an account, not a repository: one Claude or Codex login serves every repository on the machine. Two repositories that each allow three Claude runs at once leave nothing that limits the total, and the per-model concurrency of a harness (see Limiting runs of one model) limits a model, not how many runs of one harness the machine has. The pool plugin gives each repository and flow a set of named workers and gives the home one cap for each harness. It does not count runs that call a harness step directly, and it is not installed by operad init.

How the pool plugin works#

  1. The home sets settings.harnesses, the most runs one harness may have at once across all repositories and flows.
  2. A flow's settings define workers (a harness step, its args and a count) and may group them into pools; a flow that uses pool/agent (the dev flow does) calls it for each agent run.
  3. The caller passes the pool's workers in order and a key, <repository>/<pool>, under which the flow's counts are kept.
  4. pool/agent takes the first worker whose own count under that key and whose harness cap in the home both have room.
  5. The places are kept in one file under the home, pool/places.json, changed under a lock file, so every thread and process of the home sees the same counts.
  6. When no worker has room, the step waits and sends pool.waiting once for each reason: the flow's counts are full, or a harness's home cap is full.
  7. It runs the worker's harness step with the params and the worker's args, wallTimeSecs and stallSecs.
  8. It returns the harness result unchanged, with worker and harness added to data.
  9. When the model is unavailable or its usage limit is reached, or the harness cannot start, and the worker has a fallback, it runs that worker once. A timeout never falls back.

The reference for each part follows.

Agent runs cost an account, not a repository: one Claude or Codex login serves every repository on the machine. The pool plugin has one step, pool/agent, that picks a worker with room, runs that worker's harness step and hands the result back. A flow that uses it (the dev flow does) describes its workers; the home says how many runs one harness may have in all.

The plugin is shipped but not installed by operad init; operad plugin enable pool adds it.

{
  "plugins": {
    "pool": {
      "module": "@operad-io/pool",
      "settings": { "harnesses": { "pi": 2, "claude": 1 } }
    }
  }
}
SettingTypeDefaultWhat it does

A run of claude/agent counts under claude. Each count must be an integer of 1 or more; 0, a string or a fraction refuses the plugin when config.json loads, and the log names settings.harnesses. A harness that is not listed has no cap.

A change takes effect with the next pool/agent step that starts; steps already going keep their place. Only runs that go through pool/agent count: a flow that calls a harness step directly does not, and the per-model concurrency limit of the harness still applies to every run.

  • A worker is not an object, has a field not in the table, a use that is not <plugin>/<step>, args that is not a list of strings, a count that is not an integer of 1 or more, or a wallTimeSecs or stallSecs that is not above 0.

  • A fallback names an unknown worker, the worker itself, a worker that has a fallback of its own (a chain is one step; two workers that name each other are a cycle), or is not a string.

The step pool/agent#

Its params are prompt, cwd, prefix (the key for the flow's counts; the caller passes <repository>/<pool>), workers (the pool's definitions in order, each with its name), optionally fallbacks (workers outside the pool that a member's fallback names) and worker (a worker the caller requires, such as the one that did the first attempt), plus anything the harness step takes.

  1. It picks the first worker in order whose own count under prefix has room and whose harness has room under settings.harnesses. With worker set only that worker may run; a name not in workers ends the step failed with data.reason unknown_worker.
  2. When none has room it waits, without an error, until a run ends. It sends the event pool.waiting once for each reason: data.full is flow when the flow's counts are full and home when a harness's home cap is full. A stopped step leaves the line and ends interrupted.
  3. It runs the worker's use with the params, the worker's args, wallTimeSecs and stallSecs, and returns the result unchanged, adding to data: worker, harness and, after a fallback, fallbackFrom (the worker that failed).
  4. When the result's data.modelError.kind is unavailable or usage_limit, or the harness step cannot start (it threw, or it ended failed with data.reason missing or spawn), and the worker has a fallback, it runs that worker once, after giving back the first worker's places and waiting for the fallback's own room. A timeout (wall time or stall) never falls back, and the fallback's own failure is returned as it is.

Where the counts live: every step runs in its own worker thread, so the places are kept in one file under the home, pool/places.json, changed under a lock file. Steps in any thread or process of the home see the same counts. A place records the process that holds it; when that process is gone (a crashed serve) the place is dropped the next time a pool/agent step looks.

dev.json: workers and pools#

The dev plugin's work step runs every task through pool/agent, so dev needs the pool plugin enabled (operad plugin enable pool). The repository chooses its workers in <repository>/.operad/dev.json; dev reads that file in the registered repository's main clone, never the copy in a task's worktree, which carries whatever the task's branch had when it started.

FieldTypeWhat it does
workersobjectThe repository's workers. Same fields as in A flow: workers and pools; that table is the one place the worker fields, defaults and refusals are listed.
poolsobjectPool groups. A pool is a list of worker names, or an object { "workers": [...], "concurrency": n }. A work stage takes its workers from the pool its pool field names; with none it uses default, so a pools setting must define default. Without pools, default holds every worker in the order written.
concurrencyinteger, 1 or moreAn extra cap on running tasks; see below.
{
  "name": "operad",
  "remote": "origin",
  "mainBranch": "main",
  "concurrency": 2,
  "workers": {
    "claude": { "use": "claude/agent", "args": ["--model", "sonnet"], "fallback": "pi" },
    "pi": { "use": "pi/agent", "args": ["--model", "opencode-go/deepseek-v4.1-flash"] }
  },
  "pools": { "default": ["claude", "pi"] },
  "gate": { "commands": ["bash scripts/verify.sh"], "commandTimeoutSecs": 1800 },
  "check": { "rerun": 1, "flakyTask": 2 },
  "reviewer": { "use": "radian/agent", "fixLevel": "major" },
  "integration": { "style": "merge", "batch": 1 },
  "maxAutoRework": 2,
  "autoDefault": "off"
}

Errors in workers and pools name the field path, such as workers.claude.fallback or pools.default[1].

The old worker form. worker (use, args, wallTimeSecs, stallSecs) still works and means one worker named after its harness plugin (radian for radian/agent), with count equal to concurrency, alone in the pool default. Its runs count under the home cap of its harness like any worker's. A file that has both worker and workers, or pools without workers, is refused when it is read.

How many tasks run at once. Each pool has its own cap: the sum of the count of its workers, or its concurrency when that is smaller. A task counts against the pool of the flow it runs: its first work stage's pool, or default. A full code pool does not stop a task of a flow that uses another pool from starting, and the other way round. When the file sets concurrency it caps all pools together and never raises one pool's cap. A plan's own concurrency still applies on top of this. A task past a cap waits for a free place, and its row says which pool is full when the repository has more than one (waiting for the image pool's slot (T-0007)); one past a worker's own count or the home cap waits in pool/agent.

A worker listed in two pools has one count: its places are shared by both pools. A task keeps counting against the pool of the flow it started with, even if dev.json changes while it runs.

A pool whose workers have no fallback never hands its work to a worker of another pool: when the model is unavailable or its usage limit is reached, the work waits and tries again, and after the allowed waits it goes to a person. Choose a task's flow with task add --flow <name> (the command tool of MCP passes it like the CLI) or task update <id> --flow <name>; the update is refused once the task has started its first attempt.

Which worker. The work step passes the stage's pool (default unless the stage names another) and the key <repository>/<pool> to pool/agent. The attempt records the worker that ran (after a fallback, the fallback worker, with fallbackFrom naming the one that failed), and the work result says work: claude or work: pi (fallback from claude). After a rework or a reject, the next work attempt asks for the worker of the attempt before, so it resumes that worker's session when the harness can. If that worker is busy the work waits for it; another worker does not take it. If the worker is no longer in the stage's pool the pool picks any worker with room and the result says work: pi; claude is no longer in the pool.

One integration at a time#

Tasks of one repository integrate one at a time, in the order their merges were chosen. A task that waits for its turn shows waiting to integrate: T-0025 is integrating in operad running and in its step log; it holds no check place and waits without a time limit. A turn is given back when the integration ends in any way, including when its process dies.

integration.batch in dev.json (default 1, one at a time) lets a turn merge the tasks queued behind it: up to that many verified commits go onto main in queue order as one candidate, the key commands run once, and one push lands them. Each task keeps its own merge commit and its history says integrated in a batch with <tasks>. A conflict between them or a failing key command falls back to one by one, so only the task at fault goes back to its worker.

When dev.json is not valid#

A repository's dev.json is read again by every step and every scheduler pass. When the file stops being valid (a typo, or a shape the running serve does not know yet, such as after a merge changed what dev.json may hold):

  • The last valid settings of that repository stay in force. Running steps finish with them, the next step of a run reads them too, and the scheduler keeps starting and repairing tasks in that repository. A serve or a step that starts while the file is invalid reads the copy of the last valid settings kept in $OPERAD_HOME/dev/settings/. Another repository is not affected.
  • serve writes one line to its log, dev: repository "<name>": <reason>, each time the file changes to a different invalid state, never once per pass.
  • operad pending and GET /v1/pending show one item for the repository (its id is dev:settings:<name>, it has no actions): the repository settings are not valid: <reason>; the last valid settings are in use. The item disappears when the file is valid again, and the next breakage is logged again.
  • A repository that never had valid settings has nothing to fall back on: the item says so and no task starts in it until the file is fixed. Its running steps are not touched either.

When a merge changes the code serve runs#

The main clone follows a merge when it can (a fast-forward on a clean clone), but a serve that is already running keeps the code it loaded until it reloads. That is the kernel's own watch, not dev: see Changed code in the command line guide. When the code on disk differs from what serve runs and it has not taken it up, operad pending shows serve runs older code than the files on disk, whichever plugin or repository the change came from.

dev also needs the plugins its steps run through. When the home does not load pool, operad pending shows plugin pool is not loaded and dev runs its workers through it: run operad plugin enable pool and restart serve; until then no new work starts, and ready tasks stay ready instead of failing. The item goes away once pool is loaded.

What the views say about the worker#

  • operad list task and the first lines of operad show end the row's note with the worker of the task's last attempt, name only. A name longer than 16 characters is cut with …; Metrics has the whole name.
  • operad history has the work line above: work: claude or work: pi (fallback from claude).
  • The task's Metrics section adds a table under the attempts, one row per worker, summed over the attempts that worker ran: attempts, cost, time and first pass (attempts whose first review round passed, out of the attempts reviewed).
  • A task from before pools has no worker: the row shows none and Metrics has no worker table. dev has no repository-level metrics, so there is nothing to split there.
$ operad list task
T-0044-views   Worker views   running   $0.35  pi
$ operad section T-0044-views metrics
| worker | attempts | cost | time | first pass |
| --- | --- | --- | --- | --- |
| claude | 2 | $0.30 | 4m10s | 1/2 |
| pi | 1 | $0.05 | 1m02s | 0/1 |

Usage and end results#

Every agent step records what the run used in one field of its data, usage, and ends with one of a fixed list of results. Cost, metrics and budgets read this one form, whichever harness ran.

usage has these fields:

FieldTypeMeaning
harnessstringThe harness plugin that ran, such as pi.
modelstring or nullThe model as provider/id when the step named it; null when it did not.
tokens.inputinteger, 0 or moreInput tokens.
tokens.outputinteger, 0 or moreOutput tokens.
tokens.cachereadinteger, 0 or moreTokens read from the provider's cache.
tokens.cachewriteinteger, 0 or moreTokens written to the provider's cache.
costMicrosinteger, 0 or more, or nullThe cost in millionths of a dollar. null means the cost is unknown; 0 means the run was free.
costQualityexact, estimated, incomplete or nullHow far to trust costMicros. exact is the price the provider billed; estimated was worked out from a price list; incomplete priced only part of the run (some message had no price), so the real cost is higher. null exactly when costMicros is null.

A count the harness does not report is 0. Records written before this field existed keep their old fields (usage with input, output, cache_read and cache_write, and cost with micros, incomplete and estimated); they are still read, and nothing writes them any more. A usage that is not in the standard shape is ignored and the run's log gets one line naming the run and the field.

dev shows a cost's quality as a symbol in a task's row and in its metrics: $0.31 is exact, ~$0.31 is estimated and ≥$0.31 is incomplete (at least that much).

A plan's row note reads 1/8 · ~$4.20 · P2 // 2: merged tasks over tasks (cancelled ones are not counted), the total cost of the plan's tasks at the weakest quality among them (left out while no task has a cost), the priority, and after // how many of the plan's tasks may run at once. The plan's badge carries its auto level. A task's note reads $0.31 · claude · area: app-core: the cost ($0.00 before there is one), the worker, the area (or waiting for area app-core (T-0023-action-numbers)), and last a refused push's message. A repository's note reads plans: 1 · tasks: 4, counting open ones.

A step ends with one of these results:

ResultMeaning
doneThe work finished.
nothingThere was nothing to do.
failedThe step could not do its work.
needs_decisionThe step needs a person to choose.
waitingThe step stopped to wait, and will continue.
interruptedThe step was stopped before it finished.

The end results apply to plugins of the harness kind: they run an agent, and a flow reads any agent the same way. operad plugin check refuses a harness step that declares another name and names it. The agent steps of radian, pi, claude and codex declare done, failed and interrupted. Plugins of other kinds name their own results. shell is a stage, not a harness: its steps run a command or a check and give a verdict, so they end in pass and fail (and ready or waiting for a check), and the end results do not apply to them.
